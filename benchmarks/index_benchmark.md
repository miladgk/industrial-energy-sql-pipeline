# Warehouse layout benchmark

Generated by `scripts/benchmark_warehouse.py` on 2026-11-16 (PostgreSQL in Docker, local machine; median of 7 warm runs).

- Data: `fingrid_observation`, 1,304,158 rows of real Fingrid data, 19 partitions (one per month plus a default).
- Query: one week of 1-minute grid frequency (dataset 177), 2026-09-01 to 2026-09-08, 10,068 matching rows:

```sql
SELECT count(*), min(value), avg(value) FROM <layout> WHERE dataset_id = 177 AND start_time >= '2026-09-01' AND start_time < '2026-09-08'
```

| Layout | Median execution | vs. no index | Plan | Tables read | Rows read and discarded |
|---|---:|---:|---|---|---:|
| Flat table, no index | 52.31 ms | 1x | Aggregate, Gather, Seq Scan | flat_noindex | 1,294,089 |
| Flat table, primary-key index (dataset_id, start_time) | 2.25 ms | 23x | Aggregate, Bitmap Heap Scan, Bitmap Index Scan | flat_pk | 0 |
| Monthly partitions, primary-key index (fingrid_observation) | 2.00 ms | 26x | Aggregate, Bitmap Heap Scan, Bitmap Index Scan | fingrid_observation_2026_09 | 0 |

Reading it:

- Without an index PostgreSQL reads every row of every dataset and throws almost all of them away.
- The primary-key index (dataset_id, start_time) is what makes the query fast: it jumps straight to the matching rows.
- Partitioning adds pruning: the plan touches only the partition for that month, which keeps each index small as the table grows by about a million rows a year, and lets old months be dropped or archived as a whole. On a single lookup like this it is about as fast as the flat indexed table.
