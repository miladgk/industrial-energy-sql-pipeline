A data engineering case study · PostgreSQL · FastAPI · Python

Machines fail in two ways. They scream, or they go silent.

This is a working data pipeline: real Finnish grid data, and 518,400 synthetic sensor readings in PostgreSQL with a known set of deliberately broken values. It was built to find out which failures SQL can hear, and to be honest about the ones it can't.

The machine · Synthetic data

Then build a machine you can interrogate.

Twenty facilities (wind farms, solar plants and substations) with three sensors each, reporting every five minutes through January 2023. About 2% of readings are deliberately broken and labelled, so every detector can be scored against the truth.

Data model

Three normalised tables for the telemetry, one standalone table for the national grid.

  • Why recorded_at is in the primary key. PostgreSQL requires a partitioned table's unique keys to include the partition column, so readings is keyed on (reading_id, recorded_at).
  • Loading twice changes nothing. Every insert uses ON CONFLICT: existing readings are skipped, and Fingrid rows are updated in place through the unique (dataset_id, recorded_at).
  • grid_data stands alone. It holds national totals, not facility sensors, so it has no foreign key to them.

Partition pruning

readings is stored as one table per month. Pick a month: PostgreSQL reads that partition and skips the rest.

The scream · Synthetic data Injected faults

            
A spike is a scream. SQL hears every one.

            
For each sensor and month, a SQL query computes the mean and standard deviation of the clean readings. Any reading more than three standard deviations away (|z| > 3) is flagged. An injected spike is three times the sensor's normal maximum, so it is never subtle.

The silence · Synthetic data

            
A dead sensor reads zero. Usually, zero sounds normal.

            
Half of the injected faults are a sudden drop to zero. On a 110 kV bus, zero volts is impossible, and SQL catches every one. For power, wind, sunlight and temperature, zero sits inside the normal range, so the same rule hears nothing.

Run it yourself

          
Rebuilds the same 30-day dataset shown on this page (seed 42), then serves it.

          

            
git clone https://github.com/miladgk/industrial-energy-sql-pipeline.git
cd industrial-energy-sql-pipeline
cp config_template.yaml config.yaml
pip install -r requirements.txt
docker compose up -d postgres_db
python src/setup_db.py
python src/generate_data.py --days 30
python src/migrate_to_partitioned.py
DAYS_EXPECTED=30 python src/ingest.py
make api        # http://localhost:8000/docs
make test
